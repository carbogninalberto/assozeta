# Effective scheduler authority

Twenty-one source declarations are inventory, not twenty-one effective fresh
Beat schedules. With the pinned Celery 5.6.2 and django-celery-beat 2.8.1 runtime,
the namespaced `CELERY_BEAT_SCHEDULE` in Django settings takes precedence over
the twenty entries assigned to `app.conf.beat_schedule` in `core/celery.py`.
The effective configured entry is `bakney-pairing-maintenance`, every 60 seconds.
DatabaseScheduler also installs its default `celery.backend_cleanup` entry at
04:00 with a twelve-hour message expiry.

Persisted schedules are a separate authority. Startup retains custom and
historical business rows; matching configured names are reconciled with the
configured task, schedule and arguments. Existing enabled/disabled and other
model fields do not all reset together. Therefore, a fresh database cannot
establish the schedule set of an existing installation. The Go implementation
must inspect supported persisted definitions and state; it must not automatically
resurrect twenty source declarations or treat their absence from fresh startup
as proof of deprecation. The existing retirement migration disables only its
explicit four aliases, preserving association/business and custom schedules.

`TESTS/fixtures/scheduler-authority.json` specifies expected observations before
the adapter executes. `TESTS/contracts/test_scheduler_authority.py` checks exact
case sets and values without application/framework imports. The backend-specific
adapter imports actual settings, Celery and `InstanceScheduler`, migrates only
the Beat dependency schema in private PostgreSQL, and measures 29 scenarios.
Its independent initial failing report check and subsequent green observations
are retained under ignored `quality-reports/go-migration/scheduler-authority/`.
No expected report is generated by copying the adapter's observed output.

The cases cover declaration/configuration precedence, fresh bootstrap, persisted
reconciliation, rate annotations, interval/cron due decisions, disabled/start/
expiry/one-off/clocked behavior, missing initial cursors, timezone transitions,
malformed arguments/headers, configuration reload and retired aliases. Rome's
02:30 spring-gap occurrence becomes due at 03:30 local time; an already recorded
first autumn-fold dispatch prevents a second dispatch at the repeated 02:30.
These are direct ModelEntry/cron observations under controlled clocks; database
heap filtering remains a separate contract to establish. Solar rows exist, but
constructing their schedule fails because `ephem` is absent in the pinned runtime.

Delayed interval/cron schedules emit one due dispatch and advance from actual
dispatch time instead of replaying all missed slots. `*/45` in the minute field
means minutes 0 and 45, not a constant 45-minute interval. Message expiry seconds
are a publication TTL; they are distinct from an absolute schedule end time.

Publication is not atomic with Django's scheduling cursor. Reserving an entry
advances `last_run_at` and `total_run_count` before sending. An injected publisher
failure persists that advancement with zero successful publications. The actual
scheduler tick catches the send failure and continues its heartbeat. A separate
unconsumed memory-broker case verifies arguments, kwargs, exchange, routing key,
priority, headers, periodic name, publication timestamp and expiry. No business
task executes. This transport does not prove Redis persistence or recovery.

The planned Go boundary is a transaction joining owner admission, a locked source
definition/cursor, a stable occurrence identity and durable enqueue. Ownership
generation must not be part of occurrence identity, or returning ownership to Go
could duplicate work. Atomic publication would intentionally strengthen the
failed-send boundary; it cannot retroactively establish whether historical Celery
work was delivered. Installed switching still needs producer quiescence, pending
queue transfer/refusal, compatible cursor synchronization and interrupted-handoff
recovery. There is no Go scheduler or selector in this characterization increment.

Run with the exact production Python environment and integration dependencies:

```sh
python TESTS/adapters/django/scheduler_authority.py
```

The adapter checks pinned package versions, exact cases and cleanup before
publishing success. The reusable Go quality workflow requires it. Historical
backups, workflow ETA commands, task retries/rate limits, full heap selection,
broker durability and Django/Go handoff remain distinct acceptance requirements.
